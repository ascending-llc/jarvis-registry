    Skill Security Scan API¶

    Frontend reference for the advisory skill security scan and the admin control that picks the scan LLM. A frontend engineer can build the scan UI from this document alone.

    1. Overview¶

    Scans are advisory: a finding is a concern to investigate, not proof, and false positives are expected. Findings from different tools are shown side by side and are not deduplicated. Scans run asynchronously, outside the request. The UI learns a scan finished by re-fetching GET /skills/{id}/scan (or the list's scanSummary); there is no push and no polling contract. Registry content writes (create, update, file changes, GitHub sync) trigger a scan automatically. Edits made in Jarvis Chat do not, so they surface as stale: true. Skills with a supporting file stored by Jarvis Chat (every Chat-created skill with files, and any Registry skill to which Chat added a file) are never scanned and report skipped with reason chat_supporting_files_unsupported.

    2. Route prefix¶

    All paths below are relative to /api/v1.

    Scan endpoints live under the existing Skills API (/skills) and Model Gateway API (/model-gateway); they share those APIs' auth, scope and error conventions.

    3. Endpoints¶

    Endpoint Scope Skill ACL Success
    GET /skills/{skill_id}/scan skills-read VIEW 200
    POST /skills/{skill_id}/scan skills-write EDIT 202 queued · 200 already up to date
    GET /skills (existing; adds scanSummary per item) skills-read VIEW per item 200
    PUT /model-gateway/selection/skill-scan-model models-write — 200
    GET /model-gateway/selection (existing; adds skillScanModelSourceId) models-read — 200

    {skill_id} is a 24-character hex MongoDB ObjectId. A value that is not a valid ObjectId is rejected by FastAPI with 422 before the handler runs.

    Error detail shape (read this first)¶

    Two different detail shapes appear, depending on the route:

    • Skill routes (/skills/...) return a plain string detail for 401/403/404/503, and a {error, message} object only for 500.
    • Skill-scan-model route returns a {error, message} object detail for 404/409/500.

    • Scope failures (missing scope, enforced by middleware before the handler) always return the plain string {"detail": "Insufficient permissions"}.

    • 422 (FastAPI request validation) returns an array of validation errors as detail. A 422 means the client sent a bad request (a malformed skill_id, or a missing body key).

    Frontend rule: detail may be a string, an {error, message} object or (on 422) an array. Render:

    typeof detail === "string"
  ? detail
  : Array.isArray(detail)
    ? "Invalid request"
    : detail.message;

    3.2 POST /skills/{skill_id}/scan¶

    Request a manual scan. The response body is the same SkillScanResponse as GET.

    • Scope: skills-write · ACL: EDIT on the skill
    • 202 Accepted — a scan was queued (or a concurrent request already queued one). The body reflects the just-enqueued state, typically scanStatus: "pending".
    • 200 OK — nothing to queue: every enabled tool already has a succeeded or skipped result for the skill's current content. The body is the skill's current scan state, whatever its scanStatus. This is usually completed, but it can be scanning if a worker has written every result and not yet closed the job, or failed if the job failed after writing them. The body is never empty. Read scanStatus / summary, not just the status code.

    202 (queued):

    {
  "skillId": "0000000000000000000000a1",
  "skillVersion": 7,
  "scanStatus": "pending",
  "stale": false,
  "outdatedTool": false,
  "job": {
    "status": "pending",
    "rerequested": false,
    "triggerType": "manual",
    "requestedAt": "2026-11-06T12:00:00Z",
    "startedAt": null,
    "finishedAt": null,
    "attemptCount": 0,
    "errorCode": null
  },
  "summary": null,
  "results": []
}

    200 (nothing to queue): same shape as a GET response (see 3.1), typically the completed example.

    Errors: same table as 3.1, except the scope is skills-write and the ACL check requires EDIT (403 detail "You do not have EDIT permissions for this resource.").

    3.4 PUT /model-gateway/selection/skill-scan-model¶

    Set the ModelSource used as the LLM for skill scanning. It must be a chat source whose providerType is aws_bedrock or azure_openai. A null modelSourceId clears the slot (see Fallback when the slot is empty).

    • Scope: models-write · no skill ACL · Success: 200
    • Request body: SetSkillScanModelRequest. modelSourceId is required: send an explicit null to clear the slot. Omitting the key returns 422; it does not clear the slot.
    • Response body: ModelGatewaySelectionResponse.

    Set it:

    { "modelSourceId": "0000000000000000000000c1" }

    Clear it:

    { "modelSourceId": null }

    Response:

    {
  "defaultWorkflowModelSourceId": "0000000000000000000000c1",
  "embeddingModelSourceId": "0000000000000000000000e2",
  "skillScanModelSourceId": "0000000000000000000000c1"
}

    Errors (detail is a {error, message} object, mirroring set_default_workflow_model):

    Status When detail
    401 Not authenticated string, e.g. "Not authenticated"
    403 Missing models-write scope "Insufficient permissions" (plain string, from middleware)
    404 ModelSource unknown or soft-deleted {"error": "not_found", "message": "..."}
    409 ModelSource is not a chat source (e.g. an embedding source), or is a chat source whose providerType is not aws_bedrock / azure_openai (i.e. anthropic or openai) {"error": "conflict", "message": "..."}
    422 Body is missing the modelSourceId key (or is otherwise malformed) FastAPI validation error array
    500 Unexpected failure {"error": "internal_error", "message": "Internal server error"}

    Frontend note: the scan-model picker¶

    • List only chat sources whose providerType is aws_bedrock or azure_openai (SKILL_SCAN_PROVIDER_TYPES in frontend/src/pages/Models/constants.ts). Skill content must stay in the client's own cloud account (AS-1980 D7), so first-party anthropic / openai sources are never used for scanning. The backend rejects them with 409.

    Fallback when the slot is empty¶

    When skillScanModelSourceId is null, scanning uses defaultWorkflowModelSourceId only if that default is a live chat source on aws_bedrock or azure_openai. Otherwise scans run without an LLM, and LLM-backed tools report status: "partial" with statusReason: "llm_unavailable".

    Show this fallback state next to the picker when the slot is empty:

    • the default is Bedrock or Azure: "Using the default workflow model (<name>)".
    • the default is unset or is anthropic / openai: "No scan model: scans run without an LLM".

    3.5 GET /model-gateway/selection (skillScanModelSourceId)¶

    The existing selection endpoint. The body gains skillScanModelSourceId (nullable) alongside the existing two pointers. Scope models-read.

    {
  "defaultWorkflowModelSourceId": "0000000000000000000000c1",
  "embeddingModelSourceId": "0000000000000000000000e2",
  "skillScanModelSourceId": null
}

    skillScanModelSourceId: null means no dedicated scan model is set. Scanning then uses defaultWorkflowModelSourceId only if it is Bedrock or Azure, and otherwise runs without an LLM (see Fallback when the slot is empty).

    4. Data models¶

    Field names are exactly as returned (camelCase). "Nullable" means the field may be null; "optional" fields always appear but may hold a default ([], {}, false).

    SkillScanResponse¶

    Body of GET/POST /skills/{id}/scan.

    Field Type Nullable Meaning
    skillId string no Skill ObjectId.
    skillVersion integer no The skill's current version.
    scanStatus scanStatus enum no API-facing status derived from the job.
    stale boolean no summary exists and was produced for an older skillVersion.
    outdatedTool boolean no Any result came from a no-longer-configured tool/LLM.
    job SkillScanJobResponse yes The current job; null when never triggered.
    summary SkillScanSummaryResponse yes Summary of the last completed scan.
    results SkillScanToolResultResponse[] no Per-tool results of the last completed scan, ordered by tool name. Empty [] when no completed scan.

    SkillScanJobResponse¶

    Field Type Nullable Meaning
    status job status enum no pending / scanning / done / failed.
    rerequested boolean no A new trigger arrived while this job was in flight; it will re-run.
    triggerType triggerType enum no auto (content write) or manual (POST).
    requestedAt datetime no When the job was enqueued.
    startedAt datetime yes When a worker claimed it.
    finishedAt datetime yes When it reached a terminal state.
    attemptCount integer no Job-level attempts so far (max 3).
    errorCode string yes Job-level failure code when status: failed.

    SkillScanSummaryResponse¶

    Field Type Nullable Meaning
    contentDigest string no Opaque identifier of the scanned content. Not for display.
    skillVersion integer no The version this scan ran against. Compare with the top-level skillVersion for stale.
    status result status enum no Aggregate across tools (succeeded/partial/failed/skipped).
    maxSeverity severity enum yes Highest severity across findings; null when there are none.
    severityCounts object (severity → integer) no Count of findings per severity; defaults to {}.
    scannedAt datetime no When this scan completed.

    SkillScanToolResultResponse¶

    One per enabled tool for the last completed scan.

    Field Type Nullable Meaning
    tool string no Tool name, e.g. cisco-ai-skill-scanner, skillspector.
    toolVersion string no Pinned tool version that produced this result.
    status result status enum no succeeded / partial / failed / skipped.
    statusReason statusReason enum yes Why, when not plain succeeded.
    outdatedTool boolean no The result came from a scanner version or LLM model that is no longer configured.
    findings SkillScanFindingResponse[] no Findings; defaults to [].
    findingsTruncated boolean no More than 200 findings; only the first 200 are stored. Defaults to false.
    llmProviderType providerType enum yes LLM provider used (aws_bedrock/azure_openai), when the LLM pass ran.
    llmModelId string yes LLM model id used, when the LLM pass ran.
    inputTokens integer yes LLM input tokens consumed.
    outputTokens integer yes LLM output tokens consumed.
    durationMs integer yes Wall-clock run time of the tool.
    errorMessage string yes Tool-level error text, when status: failed.
    toolMetadata object no Free-form tool diagnostics; defaults to {}.
    scannedAt datetime no When this result was written (updatedAt).

    SkillScanFindingResponse¶

    Field Type Nullable Meaning
    tool string no Tool that produced the finding.
    ruleId string yes Tool-native rule identifier.
    severity severity enum no Normalized severity.
    category category enum no Normalized category.
    toolCategory string yes Tool-native category, kept alongside the normalized one.
    title string no Short finding title.
    message string no Human-readable description.
    filePath string yes File the finding is in, relative to the skill root; SKILL.md is the main file.
    startLine integer yes First line of the finding.
    endLine integer yes Last line of the finding.
    snippet string yes Offending content, ≤ 500 chars. Untrusted — render as text, never as HTML/Markdown.
    remediation string yes Suggested fix, when the tool supplies one.
    confidence number (float) yes Tool confidence, when supplied.

    SkillScanBriefResponse¶

    scanSummary on each GET /skills item.

    Field Type Nullable Meaning
    scanStatus scanStatus enum no Same mapping as the detail response.
    status result status enum yes Aggregate status of the last completed scan; null before one completes.
    maxSeverity severity enum yes Highest severity across the last completed scan.
    severityCounts object (severity → integer) no Per-severity counts; defaults to {}.
    stale boolean no As in the detail response; defaults to false.
    outdatedTool boolean no As in the detail response; defaults to false.
    scannedAt datetime yes When the last completed scan finished; null if none.

    SkillMetadataResponse.scanSummary is typed nullable, but GET /skills always populates it. A skill with no job is reported as scanStatus: "not_scanned". Check scanStatus, not null.

    5. Enums¶

    String values exactly as serialized. Use these for display text, sorting and colouring.

    scanStatus¶

    API-facing status on SkillScanResponse and SkillScanBriefResponse.

    Value Meaning
    not_scanned No job exists; never triggered (or pre-rollout).
    pending A scan is queued, not yet started.
    scanning A worker is running the scan.
    completed The job is done (job status done); read summary/results.
    failed The job exhausted its attempts.

    job status¶

    SkillScanJobResponse.status (the job's own status; done maps to completed at the scanStatus level).

    Value Meaning
    pending Queued, not claimed.
    scanning Claimed and running.
    done Finished (surfaces as scanStatus: "completed").
    failed The job could not finish after repeated attempts; not a tool failure.

    result status¶

    status on SkillScanToolResultResponse and the aggregate on the summaries.

    Value Meaning
    succeeded The tool ran fully (counts as done).
    partial The tool ran, but part of the analysis (usually the LLM pass) did not; findings are still valid.
    failed The tool errored.
    skipped The tool did not run (counts as done); see statusReason.

    statusReason¶

    Why a result is not plain succeeded.

    Value Meaning
    llm_unavailable No LLM was configured or usable for this tool.
    llm_failed An LLM was configured but its pass failed.
    llm_skipped_size_limit The orchestrator ran the tool without the LLM because the content was too large.
    analysis_incomplete The tool reports partial coverage of the content.
    chat_supporting_files_unsupported The skill has a Chat-stored supporting file Registry cannot read, so it was skipped.
    tool_error The tool itself errored.
    timeout The tool exceeded its time limit.
    parse_error The tool's output could not be parsed.

    severity¶

    severity on findings, maxSeverity on summaries. This is the sort/colour order (critical highest → info lowest).

    Value Meaning
    critical Highest-risk finding.
    high High risk.
    medium Moderate risk.
    low Low risk.
    info Informational — not a security finding.

    category¶

    Normalized finding category.

    Value Meaning
    prompt_injection Content that tries to hijack the agent's instructions.
    data_exfiltration Sending data to an external destination.
    command_execution Executing shell / system commands.
    credential_access Reading secrets, keys or credentials.
    obfuscation Hidden or encoded content masking intent.
    supply_chain Risky dependency or package behaviour.
    excessive_permissions Requesting more access than the task needs.
    harmful_content Content that could harm the user or others.
    social_engineering Manipulating the user into unsafe actions.
    other Does not fit the categories above.

    triggerType¶

    SkillScanJobResponse.triggerType.

    Value Meaning
    auto Enqueued by a Registry content write.
    manual Enqueued by POST /skills/{id}/scan.

    llmProviderType¶

    llmProviderType on a tool result (the ModelSource provider that backed the LLM pass).

    Value Meaning
    aws_bedrock AWS Bedrock-hosted model.
    azure_openai Azure OpenAI-hosted model.

    6. Semantics the UI must respect¶

    • stale: true — the skill changed (usually in Jarvis Chat) after the last scan. The summary/results describe an older version. Offer a manual rescan (needs EDIT).
    • outdatedTool: true (top level or per result) — the result came from a scanner version or LLM model that is no longer configured. Repointing the same modelSourceId at a different deployment (region, endpoint, api version) also counts. It is still shown until the next scan replaces it.
    • summary reflects the last completed scan. While scanStatus is pending or scanning, summary and results may still hold the previous scan — do not assume they match the current content.
    • A partial result still has valid findings. It means part of the analysis (usually the LLM pass) did not run; statusReason says why. Do not hide its findings.
    • Findings are not deduplicated. Different tools are independent and may describe the same issue twice. Group by tool, not by assuming uniqueness.
    • findingsTruncated: true — the tool reported more than 200 findings; only the first 200 are stored. Tell the user the list is capped.
    • snippet is untrusted skill content, capped at 500 characters. Render it as plain text — never as HTML or Markdown.
    • filePath is relative to the skill root; SKILL.md is the main file.
    • A POST that returns 200 did nothing — every enabled tool already has a succeeded or skipped result for the current content. Only 202 means a new scan was queued.
    • failed scanStatus (job attempts exhausted) is not the same as a failed tool result. Both can be retried with POST by a user with EDIT.

    7. Access control¶

    Two layers: an OAuth scope (checked by middleware before the handler) and, for the skill endpoints only, an ACL permission on the specific skill (VIEW to read, EDIT to scan).

    Scopes come from registry-pkgs/src/registry_pkgs/scopes.yml group_mappings:

    Endpoint jarvis-registry-admin -power-user -user -read-only
    GET /skills/{id}/scan (skills-read) ✅ ✅ ✅ ✅
    POST /skills/{id}/scan (skills-write) ✅ ✅ ✅ ❌
    GET /skills (skills-read) ✅ ✅ ✅ ✅
    PUT /model-gateway/selection/skill-scan-model (models-write) ✅ ❌ ❌ ❌
    GET /model-gateway/selection (models-read) ✅ ✅ ✅ ✅
    • Only jarvis-registry-admin has models-write, so only an admin can pick the scan model.
    • Reading a scan additionally needs VIEW on the skill; requesting one needs EDIT. Having the scope but not the ACL permission returns 403 with a plain-string detail naming the missing permission.
    • GET /skills applies VIEW per item, as it does today; a user sees scanSummary only for the skills they can view.
